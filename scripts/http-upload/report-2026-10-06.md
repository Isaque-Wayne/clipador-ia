# Evidências de upload HTTP — 2026-10-06

Relatório histórico da execução com limite de 50 MiB. O limite foi posteriormente
alterado para 4 GiB; as medições abaixo permanecem referentes à execução original.

Ambiente local Windows, Node.js 24.21.0, Next em modo produção. API em 127.0.0.1:3011 e web em 127.0.0.1:3010, sem interromper o processo que já ocupava 3001. Storage isolado; concorrência 2; timeout 90.000 ms. Requisições POST e GET passaram pelo web/proxy, sem chamar diretamente as rotas da API.

**Resultado: 11 cenários HTTP passaram, nenhum falhou.** A camada navegador não foi executada: a sessão não disponibilizou navegador controlável. A página `/upload` respondeu HTTP 200, mas isso não comprova interação com o formulário.

## Cenários

| Cenário | Resultado observado |
| --- | --- |
| MP4 pequeno (1.128.375 bytes) | 200, metadados e SHA-256 corretos; envio em 54,8 ms |
| MIME/extensão inválidos | 415 |
| Arquivo vazio | 400 |
| 49,5 MiB com envio lento | 200, SHA-256 correto; 12,30 s |
| 50 MiB + 1 byte, Content-Length | 413 antes de gravar o vídeo completo |
| 50 MiB + 1 byte, chunked | 413 durante streaming; sem parcial restante |
| Reinício da API | GET pelo ID retornou 200 e o mesmo checksum persistido |
| Dois uploads de 48 MiB simultâneos | Ambos 200 em aproximadamente 11,96 s; terceiro 429; novo envio 200 após conclusão |
| Desconexão após aproximadamente 1 MiB | Parcial removido, bytes retornaram ao valor anterior, nenhum metadata/índice novo, GET 404; próximo envio 200 |
| Timeout com stream pausado | 408 em 90,04 s; parcial removido, bytes e quantidade de metadados inalterados; próximo envio 200 |
| Quota após recuperação | Limite configurado em bytes existentes + 100; novo upload 507; disco inalterado |

Os sete vídeos completos conservados ao fim da execução tiveram SHA-256 recalculado independentemente com `Get-FileHash`: todos coincidiram com `metadata.json`, após os reinícios da API.

## Medições

| Operação | RSS mínimo–máximo da API | Pico de ArrayBuffers | Tempo do upload |
| --- | --- | --- | --- |
| Um vídeo de 49,5 MiB | 74,58–88,17 MiB | 7,67 MiB | 12,30 s |
| Dois vídeos de 48 MiB | 81,85–95,93 MiB | 14,71 MiB | ~11,96 s cada |
| Stream parado até timeout | 72,20–84,54 MiB | 2,63 MiB | 90,04 s |

Os picos observados não indicam retenção integral dos vídeos na RAM da API. RSS inclui runtime, buffers e efeitos do GC; os intervalos não são crescimento líquido nem limites garantidos. Amostras a cada 200 ms podem perder picos breves, e a memória do processo Next não foi medida.

Disco final: **157.083.537 bytes (149,81 MiB)**, incluindo vídeos e JSON. Nenhum `.part` restante. Desconexão retornou a 154.826.151 bytes e timeout retornou a 155.954.844 bytes antes dos respectivos envios seguintes de confirmação; esses envios explicam o aumento nos snapshots finais dos cenários. Quota foi também validada pelos testes automatizados de reservas concorrentes.

## Validação adicional

- 34 testes da API/worker passaram.
- 2 testes do proxy web passaram.
- `pnpm.cmd typecheck` passou.
- `pnpm.cmd build` passou para API, web e worker; o build final restaurou a rewrite para a API habitual na porta 3001.

Nenhum bug de produção foi encontrado nos cenários executados. Nenhuma dependência instalada ou arquitetura alterada. A primeira tentativa de iniciar a API encontrou a porta 3001 ocupada; os testes usaram portas separadas. Os scripts de teste receberam correção de codificação dos textos, sem alteração de comportamento.

## Artefatos e limites

Evidência bruta local: `apps/api/.data/http-runs/2026-10-06T15-15-09-154Z/results.json`, com amostras de memória, tempos, respostas, IDs e bytes em disco; logs ao lado. Esses artefatos são ignorados pelo Git e permanecem disponíveis para inspeção.

Fixture: MP4 público usado nos [exemplos de vídeo da MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video). Os arquivos grandes usam padding; não houve decodificação, validação de codec ou FFmpeg.

Teste local curto não comprova estabilidade prolongada, comportamento em múltiplos processos/instâncias nem desempenho sob outra rede ou proxy. Timeout foi medido com stream pausado depois do início, e não com um envio contínuo que dura mais de 90 segundos. Não foi simulado encerramento abrupto do processo durante escrita; recuperação foi testada com reinício normal.

O backend passou pelas verificações necessárias para uma integração experimental com um consumidor. **A etapa completa ainda depende do teste real no navegador.** O próximo passo é concluir essa validação visual e, depois, conectar um processamento mínimo usando o contrato de consumo que verifica integridade antes de acessar o arquivo.
